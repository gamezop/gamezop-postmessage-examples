# Web iframe example

[`index.html`](index.html) is one self-contained HTML/CSS/JavaScript page with no
build tools or third-party runtime dependencies. It opens a game in an iframe
and inspects its `window.postMessage` callbacks.

## Run

For a local UI check, from the repository root run:

```sh
python3 -m http.server 8080 --bind 127.0.0.1 --directory web
```

Open `http://localhost:8080/`. For real integrations, serve `web/index.html` from
your own HTTPS origin. Some Gamezop callback configurations require an HTTPS
parent referrer and will not send events to an HTTP localhost parent. Merely
opening a `file://` URL is not a supported integration setup.

1. Ask Gamezop to enable client broadcasts for your Web property.
2. Choose **Individual** or **Battles**, then paste your final HTTPS game URL.
3. For Battles, include one Base64-encoded non-empty `roomDetails` JSON object,
   generated by your integration; join from multiple clients with different users.
4. Select **Launch**, play, and toggle the draggable **Logs** pill.
5. Select an event to inspect fields and JSON. **Copy JSON** uses the system
   clipboard; **Clear** removes the in-memory log. Reload reloads the iframe,
   not the parent page, and does not clear the log.

The two launcher modes retain separate input values. The inspector keeps the
newest 500 entries; unknown events and malformed JSON remain visible.

### Direct launch

The page accepts `mode=individual|battles` and a URL-encoded `url` parameter:

```js
const demoUrl = new URL('https://your-host.example/index.html');
demoUrl.searchParams.set('mode', 'battles');
demoUrl.searchParams.set('url', finalGameUrl); // URLSearchParams performs encoding.
```

Replace both example host and `finalGameUrl` with values from your integration.
Missing `url` shows the launcher; invalid input shows validation errors.

## Callback: parent, method, and target origin

| Role | Value |
| --- | --- |
| Receiver | The parent page containing `#game-frame` |
| Sender | The Gamezop page inside that iframe |
| Sender method | `window.parent.postMessage(payload, targetOrigin)` |
| Receiver listener | `window.addEventListener('message', handler)` |
| `targetOrigin` | The parent's HTTPS origin, not the game origin |
| Accepted payload | Object or stringified JSON in `event.data` |
| Required checks | Exact iframe `contentWindow` **and** configured game origin |

See the [callback reference and copyable snippets](../docs/callback-configuration.md#web).
No Android bridge or iOS handler is registered by this Web page. Ask Gamezop to
enable callbacks once; the same listener receives Individual and Battles events.

## Browser security and troubleshooting

- The iframe allows fullscreen, autoplay, and gamepad features, subject to browser
  policy. A tap may still be necessary to start media.
- `referrerpolicy="strict-origin-when-cross-origin"` lets an HTTPS Gamezop frame
  receive the embedding origin without the parent's URL path/query. Do not use
  `no-referrer` with a sender that derives its callback destination from referrer.
- `event.source` must equal the active iframe's `contentWindow`, and `event.origin`
  must equal the initially configured game origin. Redirecting to another host
  can make a game visible while its events are rejected; use an appropriate final
  URL confirmed by Gamezop. Do not broaden the check to `*`.
- The parent cannot inspect or intercept arbitrary navigation inside a
  cross-origin iframe. Unlike mobile WebViews, this example cannot enforce the
  mobile host allowlist on subsequent iframe navigation.
- CSP `frame-ancestors` or `X-Frame-Options` may forbid embedding. The parent
  cannot override those response headers, and iframe `load` does not prove the
  game rendered successfully. Inspect browser console/network errors.
- Clipboard access may be blocked by browser permissions or insecure hosting;
  the page attempts a fallback. Prefer HTTPS and a user-initiated copy action.

The event log is memory-only, but the launched game URL is placed in the parent's
address bar via `history.replaceState`. It may appear in browser history, copied
links, screenshots, or hosting access logs when a deep link is opened. Base64 is
not encryption; do not include secrets in room details or publicly share real
player payloads. The iframe can also use normal browser cookies and web storage.

## Manual verification

- Test launcher and query launches in both modes; reject HTTP, credentials,
  missing/duplicate `roomDetails`, and malformed Base64/JSON.
- Play a broadcast-enabled game and confirm both object and JSON-string messages
  are handled. Messages from other frames/origins must not appear.
- Inspect known, unknown, and malformed entries; check the 500-entry limit,
  selection, copy, and clear.
- Drag/toggle Logs and resize/rotate the viewport without recreating the iframe.
- Reload the game and confirm the parent and existing log remain intact.

There is no committed automated browser test runner. See the shared
[event meanings](../docs/event-contracts.md) when checking actual payloads.
